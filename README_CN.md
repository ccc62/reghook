# RegHook v6.4 多规则增强版（ARM64 / ptrace 硬件执行断点）

> 实验版本。此前用户报告 v4 在其设备上成功修改寄存器并观察到游戏内效果；v6.3 的多规则实现尚未在真实 Android ARM64 设备上完成回归测试。请先在自己有权调试的测试进程中验证。错误的寄存器修改可能导致目标进程异常。

## v6.4 新增功能

1. **PID / 包名选择**：目标输入支持 PID、包名（如 `com.example.app`），扫描 `/proc/*/cmdline` 进行匹配。若匹配到多个进程（包括 `:service` 子进程），会列出候选项并要求输入列表中的 PID，不会盲选。
2. **真正暂停/继续断点监控**：监控时输入 `P` 并按 Enter，程序会短暂中断已跟踪线程、暂时禁用本程序安装的硬件执行断点，然后恢复线程运行；暂停期间目标进程继续运行，但不会触发本程序已禁用的执行断点。输入 `C` 并按 Enter，重新启用仍处于活动状态的规则。
3. **实时刷新**：输入 `R` 并按 Enter，显示全局与分规则命中/写回统计及当前暂停状态。
4. **交互退出**：输入 `Q` 并按 Enter，进入清理流程；`Ctrl+C` 仍可停止。
5. **暂停切换诊断**：如果某线程无法停止或硬件状态无法更新，会输出警告并尽量回滚到之前的逻辑状态；切换失败时不应把它视为成功暂停/继续。

## v6.3.2 修复内容

1. **修复多规则断点状态串扰**：区分规则配置状态和线程当前实际状态。某条规则单步期间暂时禁用时，重新启用另一条规则不会再基于“全部启用”的模板意外重新打开它。
2. **补充单步异常诊断**：单步停止状态不符合预期且 PC 未离开断点地址时，日志会输出停止信号、`si_code` 和 PC；该线程的对应规则会停用以避免热循环。此策略是保护措施，不代表已查明停止原因。
3. **增加按 TID 的命中分布**：退出时显示发生过命中的线程及各规则命中次数，便于判断事件是否集中在少数线程。
4. **统计口径说明**：执行断点命中数统计到达指定指令地址的事件；它不等同于某个特定内存地址的写入次数。

## v6.3 功能

1. **多地址规则**：一次可配置 1–8 条规则，每条规则独立设置断点地址、寄存器和写入值；写入值可选择十六进制或十进制。
2. **支持 X/W 寄存器写法**：可输入 `X8`、`W11` 或数字 `8`。`Xn` 写入完整 64 位值；`Wn` 只写低 32 位，等效于写 W 寄存器。
3. **逐规则统计**：启动时显示每条规则成功安装到多少线程；退出时分别显示每条规则的命中数和写回失败数。
4. **按规则单步**：命中某条规则后只暂时关闭该线程上对应的断点，修改寄存器、单步执行，再重新启用对应断点。
5. **硬件槽位检查**：读取每个线程可用的硬件执行断点槽位；槽位不足时会跳过无法安装的规则，并显示各规则实际安装到的线程数，不会声称所有规则都已安装。
6. **保留 v6.2 的安全处理**：地址映射检查、超长输入处理、异常 SIGTRAP 转发、单步异常保护、失败统计和清理恢复。

## 使用方法

1. 输入目标 PID（十进制）或包名（例如 `com.ztgame.bob`）。如果包名匹配多个进程，按提示选择候选 PID。包名识别依赖 `/proc` 可读；在 Android 上通常需要合适的权限。

2. 输入规则数量，范围为 1–8。
3. 每条规则依次输入：断点地址（十六进制）、寄存器（`X0`–`X30` 或 `W0`–`W30`）、数值进制（`1` 十六进制 / `2` 十进制，直接回车默认十六进制），最后输入写入值。十六进制可输入 `1388` 或 `0x1388`；十进制直接输入 `5000`。
4. 确认配置，程序等待 3 秒后附加当前线程并安装断点。
5. 监控中可输入 `P` 暂停、`C` 继续、`R` 刷新统计、`Q` 停止；命令都需要按 Enter。暂停/继续时程序会短暂中断当前跟踪线程来修改硬件断点状态，但随后会恢复线程运行。按 `Ctrl+C` 也会停止，程序会尝试恢复原硬件断点状态并分离线程。

输入 `q` 可返回上一步；PID 输入 `q` 退出。地址必须非零且 4 字节对齐；如果 `/proc/<PID>/maps` 可读取，地址还必须位于目标进程的可执行映射中。

## 选择断点位置的重要说明

硬件执行断点在指定指令**执行前**触发。如果要修改一条指令计算或加载后的结果，通常应把断点放在该指令的**下一条指令**上：

- 想改 `LDUR W11, [X29,#-0x14]` 加载后的 W11，可考虑在下一条指令地址 `0x...D95C` 断下，再修改 W11。
- 想改 `MOV X10, #0x58C4` 执行后的 X10，可考虑在下一条指令地址 `0x...D954` 断下，再修改 X10。
- 想改 `ADD W9, W9, W0` 的计算结果，可考虑在下一条指令地址 `0x...D940` 断下，再修改 W9。
- 若在 `STR W8, [X9,X10,LSL #0]` 本身执行前断下，则修改 W8 会影响即将写入的值。

以上地址仅对应示例汇编现场；模块基址、ASLR、进程重启或版本更新后地址可能变化。修改 X10 这类地址索引寄存器会改变后续内存访问位置，使用前务必确认目的。

## 暂停功能说明

- 暂停期间只禁用本程序安装的硬件执行断点，不会主动暂停整个目标进程；线程会恢复运行。
- 为了安全修改各线程的硬件断点寄存器，按下 P/C 的切换过程中会短暂中断已跟踪线程。切换失败会输出诊断，不能把警告当作成功。
- 暂停期间不会记录或处理由这些已禁用执行断点产生的命中，因为它们不会被触发；继续后只恢复仍处于活动状态的规则。
- 如果某条规则此前因单步异常而在某个线程上被停用，C 不会擅自重新启用该条已停用规则。

## 已知限制与风险

- ARM64 每个线程的硬件执行断点槽位数量有限且由内核/硬件决定；本程序最多接受 8 条规则，但不保证每个线程都能安装 8 条。请检查启动时的每规则安装线程数。
- 不自动跟踪启动后新建的线程。
- 不同线程可能可用槽位不同，因此同一条规则不一定安装到所有线程。
- 单步异常或断点重新启用失败时，程序可能主动停止该线程上对应规则的监控，以避免重复触发。
- 若清理时无法确认线程停止，程序会报告严重警告；此时不能保证成功恢复硬件状态或分离关系。
- Android 厂商内核对 ptrace、硬件断点和单步信号的行为可能不同。
- 当前环境完成了主机端 Clang/GCC 语法检查和 GCC 静态分析，但没有完成真正的 Android NDK ARM64 交叉编译，也没有在 MIX 4 上完成 v6.4 设备回归。包名识别和 P/C 暂停/继续仍需在你的设备上验证。请先通过 GitHub Actions 构建，保留 v4/v5/v6.3.1 备份，并在可恢复的自有测试进程中验证。

## 构建

将 `reg_hook.c`、`README_CN.md` 和 `.github/workflows/build.yml` 放在 GitHub 仓库根目录。进入 Actions 运行 **Build RegHook v6.4 ARM64**。工作流使用 Android NDK 编译 `aarch64-linux-android24`，并上传二进制和源码 ZIP。
